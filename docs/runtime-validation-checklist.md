# StorageSign 実動作確認チェックリスト

このチェックリストは、実サーバーでの運用前確認向けです。搬送ブロック対応
（ホッパー/ドロッパー/ディスペンサー/クラフター/ホッパー付きトロッコ/チェスト付きトロッコ/
チェスト付きボート）の回帰に加え、Potion 表示と外部 Logger 障害注入のような
手動確認が残る項目もここで扱います。

## 0. 事前準備

- [ ] サーバーを停止し、ビルド済み JAR を `plugins` に配置する
- [ ] `config.yml` の `auto-import: true` / `auto-export: true` を確認する
- [ ] 検証用ワールドで以下を準備する
  - [ ] 隣接コンテナ（チェスト等）
  - [ ] 対応アイテム登録済み StorageSign
  - [ ] ホッパー、ドロッパー、ディスペンサー、クラフター、ホッパー付きトロッコ、チェスト付きトロッコ、チェスト付きボート

## 1. 基本回帰（既存ホッパー）

- [ ] ホッパーでコンテナへ投入したとき、満杯分が SS に吸収される
- [ ] ホッパーでコンテナから搬出したとき、1 ティック後に SS から補充される
- [ ] ログに異常（例外、NPE）が出ない

## 2. Inventory 間搬送（新規対象）

### 2.1 ドロッパー

- [ ] SS 隣接コンテナへ搬送したとき、インポート（吸収）が機能する
- [ ] SS 隣接コンテナから結果的に搬出される経路で、エクスポート（補充）が機能する

### 2.2 ディスペンサー

- [ ] SS 隣接コンテナへの搬送でインポートが機能する
- [ ] SS 隣接コンテナからの搬出経路でエクスポートが機能する

### 2.3 クラフター

- [ ] クラフター排出サイクルで SS 在庫同期が機能する
- [ ] 連続駆動でも在庫表示と実在庫が乖離しない

### 2.4 ホッパー付きトロッコ

- [ ] SS 近傍通過時に搬送経路として認識される
- [ ] インポート/エクスポート動作が固定ホッパー経路と同様に機能する

### 2.5 チェスト付きトロッコ

- [ ] SS 近傍通過時に搬送経路として認識される
- [ ] インポート/エクスポート動作が固定ホッパー経路と同様に機能する

### 2.6 チェスト付きボート

- [ ] SS 近傍通過時に搬送経路として認識される
- [ ] インポート/エクスポート動作が固定ホッパー経路と同様に機能する

### 2.7 Brewing Stand

- [ ] Blaze Powder が燃料スロットへ補充される
- [ ] Potion が 3 つの Potion スロットへ補充される
- [ ] 有効な醸造材料だけが材料スロットへ入り、非対応品は拒否される

### 2.8 Furnace系

- [ ] Furnace / Blast Furnace / Smoker で燃料が燃料スロットへ補充される
- [ ] Furnace系で入力アイテムが入力スロットへ補充される

## 3. ワールド吐き出し（BlockDispenseEvent）

- [ ] ドロッパーのワールド吐き出し時、SS 在庫が減算される
- [ ] ディスペンサーのワールド吐き出し時、SS 在庫が減算される
- [ ] クラフターのワールド吐き出し時、SS 在庫が減算される
- [ ] SS 残量不足時でもイベントが停止せず、同期可能分のみ減算される

## 4. 非対応ソースの確認

- [ ] 対応一覧に含まれないブロックでは SS 同期処理が走らない
- [ ] 既存の手動入出庫、autocollect、クラフト機能に回帰がない

## 5. 境界ケース

- [ ] ラージチェスト（DoubleChest）でも隣接判定が崩れない
- [ ] 看板の向き（立て看板/壁看板/吊り看板）で判定漏れがない
- [ ] サーバー再起動後に SS 表示値が正しい
- [ ] 通常・壁・吊り・壁掛け吊り看板でPotion短縮表示が枠内に収まる
- [ ] Potion看板を破壊・再設置しても種類、延長・強化、数量が維持される
- [ ] 標準フォント以外のリソースパックを使う場合は表示のはみ出しを個別確認する

### 5.1 再起動時の独立永続化確認

- [ ] 再起動前に `storage-sign-index.bin` を外部CLIの `inspect` / `search` で読み、対象SSのWorld UUID・座標・識別子・数量を保存する
- [ ] サーバーを再起動し、ゲーム内検索だけでなく外部CLIでも同じレコードを再読込できる
- [ ] 対象看板のPDCを外部NBT確認手段でも読み、完全識別子が表示短縮文字列ではなく正規値のまま維持される
- [ ] E2E要約が `observation=client` か `mixed-client-and-synthetic` かを記録し、後者をクライアントpacket確認済みとして扱わない

### 5.2 銅ゴーレムの像

- [ ] 像を持つPaper版で `./scripts/test.sh e2e 1.21.11 without-logger` を実行し、酸化4段階×ワックス有無の採掘ドロップが登録・搬入・搬出できることを確認する
- [ ] 独自名・PDC付きの像は登録できず、数量とメタデータが失われないことを確認する
- [ ] 実サーバーで使う像に名前や独自データがある場合、その実物で確認する。名前付きMobから像への変化は別途確認する
- [ ] ポーズE2Eで8素材×4ポーズの実採掘ドロップがすべて個別に登録・収納・復元でき、素材ごとに4つの識別子になることを確認する
- [ ] 異なるポーズは相互に混入せず、手持ちの数量・ポーズを失わないことを確認する
- [ ] ポーズ別SSの分割・再統合、サーバー再起動後もポーズと数量が維持されることを確認する
- [ ] 別プラグインでアイテム化するゴーレムは、プラグイン名・版と実際のItemMetaを記録して個別確認する

対応前の2026-10-16のPaper 1.21.11診断ではstanding以外は登録拒否だった。
対応後は全ポーズの成功を必要条件とする。

2026-10-17の `./scripts/test.sh e2e 1.21.11 without-logger` はmain・restartとも成功。
32組の個別登録・往復、4ポーズの分割・再統合・再起動後の復元を確認した。
クライアント操作とBukkitイベントfallbackの混在検証（fallback 9回）であり、
手動クライアント確認やSpigot確認を代替する結果ではない。

### 5.4 ミツバチの巣・養蜂箱の蜜の量

- [ ] ミツバチなしの巣・養蜂箱を蜜レベル0～5でシルクタッチ採掘したドロップから、各16個を登録・搬入・搬出できることを確認する
- [ ] `BEE_NEST[honey_level=5]` のように蜜レベル別の識別子になり、取り出したアイテムが元の採掘ドロップと完全一致することを確認する
- [ ] ミツバチ入りの巣・養蜂箱の新規登録を拒否し、手持ちのミツバチとアイテムを失わないことを確認する

2026-10-17のPaper 1.21.11絞り込みE2Eで、ミツバチなしの2素材×6段階の
登録・16個の搬入・搬出とItemMeta完全一致が成功した（MAT-25）。
蜜レベル0の実ドロップは明示状態を省略していた。合成イベントfallbackは1回。

## 6. 外部 Logger 障害注入

この項目は外部 Logger のファイル管理に関する手動確認であり、StorageSign の自動E2Eとは分離する。
事前に `config.yml` の `log-level` を `DEBUG` へ変更し、StorageSign を再起動してから確認する。

- [ ] 検証用サーバーへ Logger を導入し、StorageSign の DEBUG ログが保存先へ到達する
- [ ] 保存先を読取専用にして書込みを発生させても、右クリック入出庫とHopper搬送が継続する
- [ ] Logger のローテーション閾値を検証用の小さい値に設定し、切替後のファイルへ記録が継続する
- [ ] 書込み失敗時に Paper または Logger の標準ログから原因を診断できる
- [ ] 権限を戻して Logger とStorageSignを再起動し、外部Logger登録と書込みが復旧する

合格条件は、Logger障害によってStorageSignの数量・アイテムが失われず、障害原因を標準ログから
追跡できること。Loggerファイルの生成・ローテーション自体の成否は外部Logger製品の責任範囲とする。
